The Problem

Centralized key management is broken

Every AI app, SaaS tool, and automation pipeline needs API keys. But the way we store and use them today has fundamental flaws.

🔑

You hand keys to strangers

When you paste your OpenAI or Anthropic key into a chatbot or agent platform, that key sits on their server. One breach and it's gone.

💸

Abuse is too easy

A competitor or a malicious actor can spam your endpoint with useless requests and run up a massive bill. You won't know until the invoice arrives.

🔒

Vendor lock-in

Composio, Fga.dev, and others build walled gardens. Your keys, your tools, your workflows — all locked behind their auth layer and their pricing.

🧩

No smart routing

You have an Anthropic key and an OpenAI key. Today you pick one manually. There's no protocol that says "use Claude for code, GPT for summaries, cheapest for simple tasks."

The Solution

A self-sovereign key wallet on Swarm

SwarmKey stores your API keys as encrypted chunks on the Swarm network. Only you can decrypt them — with your seed phrase. An agent runtime reconstructs the key locally, calls the API, and the key never touches a server.

1

Encrypt & shard

Your key is split into encrypted fragments and uploaded to Swarm with Access Control (ACT).

2

Store on Swarm

Fragments live as content-addressed chunks. ~$0.20/year to store. No server owns them.

3

Reconstruct locally

Your browser or agent runtime uses your seed phrase to pull and decrypt shards — locally.

4

Call the API

The runtime calls the LLM (or any API) directly. The key exists only in memory, for milliseconds.

Two-Layer Architecture

Your keys stay private. Discovery stays open.

SwarmKey has two independent layers:
Layer 1 — Vault: Your API keys encrypted on Swarm (ACT). Never leaves your control.
Layer 2 — Discovery: Query any ARD-compliant registry to find capabilities you don't have yet.
Inspired by Agentic Resource Discovery (ARD) — the open standard for federated agent resource discovery.

When a website needs a capability, the router first checks your vault. If you have an Anthropic key and the task is "text completion," it routes there immediately — no discovery needed.

If the capability isn't in your vault, the router queries external ARD registries — GitHub Agent Finder, Hugging Face Discover, Ora Directory, Cisco AI Catalog — to find resources that provide it. It returns matches with their endpoints, parameters, and trust signals. You decide whether to add the key.

This is the ARD model: publish once, discover everywhere. Resources describe themselves at /.well-known/ai-catalog.json. Any ARD client can index them. No central gatekeeper. No per-collection re-registration.

Vault + ARD: why both matter

🔑 Vault = zero-trust credential storage

Your keys are encrypted on Swarm via ACT. Only you can decrypt them. No server ever sees plaintext. MCP transport supported natively — JSON-RPC connections established locally.

🔍 ARD = open capability discovery

When you lack a key, query GitHub Agent Finder, HF Discover, Ora, or Cisco catalogs. They return ARD-compliant entries with URN identifiers, trust manifests, and endpoint URLs. You choose what to install.

🏷️ Capability-based routing

Websites declare "I need geocoding", not "Use Mapbox". Router checks vault → if present, use it. If absent, query ARD registries → found? Prompt user to add key → done.

🌐 Federated, not centralized

ARD registries crawl /.well-known/ai-catalog.json across the web. Each resource describes itself once. Any client can index it. No single operator controls discovery.

🛡️ Trust via trustManifest

ARD entries carry SPIFFE/DID identities and compliance attestations (SOC2, GDPR). Ora Directory even provides agent-readiness scorecards signed as Ed25519 JWS. Verify before you add a key.

⚡ Works today

GitHub Agent Finder (agentfinder.github.com), HF Discover CLI (hf discover search), Ora Directory (ora.ai/api/ard/search), Cisco AI Catalog (ai-catalog.outshift.io) — all ARD-compliant, all queryable now.

P2P Toolset Registry

A decentralized catalog of tools

Composio has a tool registry. Fga.dev has a policy registry. Both live on their servers. SwarmKey's registry lives on Swarm — content-addressed, versioned, and impossible to take down.

👤 User (seed phrase)
↓
🐝 Swarm (content-addressed) bzz://<hash>/manifest.json
↓
📋 Tool Manifest tools, schemas, policies
↓
🤖 Agent Runtime (local) reconstructs key, calls API

📦 Content-addressed

Every tool manifest has a Swarm hash. If someone tampered with it, the hash changes. You always get exactly what was published.

📜 Versioned & immutable

Swarm's history feature preserves old versions. You can pin a specific manifest version and know it will never change under you.

🔓 Access-controlled (ACT)

The publisher grants access to specific users via public keys. Revocation is instant. Only authorized users can read the manifest.

🌐 No central server

No single point of failure. No one can shut it down, censor it, or change the terms. The registry is the network.

🔗 Composable

Tools reference other tools by hash. Build complex agent workflows by chaining manifests — all verifiable, all decentralized.

💸 ~$0.20/year

A typical tool manifest + key shards costs pennies to store for a year. No subscriptions, no per-request fees to a registry operator.

FAQ

Questions you probably have

If the key is on Swarm, can't anyone read it?

No. Keys are encrypted at the chunk level using Swarm's Access Control Trie (ACT). Only grantees whose public keys are in the access list can decrypt. Even if someone downloads the chunk, they see only ciphertext.

What if Swarm goes down?

Swarm is a decentralized network of Bee nodes — there's no single server to go down. As long as nodes are online (and they are, incentivized by postage stamps), your data is reachable. You can also run your own Bee node for guaranteed availability.

How does routing work with just one key?

The router doesn't pick between providers — it picks the best model from your existing key's lineup. If you have an Anthropic key, it routes code tasks to sonnet-4 and simple chat to haiku. For tasks your LLM can't handle (maps, STT, image gen), it detects the gap and either suggests adding a specialized key or uses a workaround.

How is this different from a password manager?

Password managers (1Password, Bitwarden) store secrets on their servers or in a synced vault. SwarmKey stores them on a decentralized network with no central operator, and the agent runtime reconstructs keys locally at call time — no app ever holds the plaintext key in a database.

Is this legal / compliant?

SwarmKey is a protocol, not a service. It doesn't custody keys — the user does. From a GDPR perspective, the user controls their own data. From an API ToS perspective, the user is calling the API directly with their own key, which is the intended use.

How much does it actually cost?

Storing ~13 KB (a manifest + 3 key shards) for a year on Swarm costs roughly $0.20 at current postage stamp rates. There are no per-request fees — you call the LLM API directly, paying the provider's normal rate.

Can I use this with any API, not just LLMs?

Yes. SwarmKey is API-agnostic. Any key or OAuth token — Stripe, GitHub, Notion, AWS — can be stored and routed. The policy manifest defines categories, so you can route "payment" to Stripe, "search" to Brave, and "code" to Claude.

What's the developer experience?

A simple SDK: npm i @swarmkey/agent. Provide your seed phrase, load a manifest by Swarm reference, and call agent.run("Summarize this page"). The SDK handles retrieval, decryption, routing, and the API call.

Is this live today?

This is a concept demo illustrating the protocol design. The Swarm infrastructure (ACT, postage stamps, Bee nodes) is live and production-ready. The SwarmKey SDK and reference implementation are the proposed next step.
